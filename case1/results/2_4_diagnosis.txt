1. THE FAILING INSTRUCTION
--------------------------------------------------------------------------
  With the linkage table resolved and the runtime modelled, but no
  call-site resolution, the longest surviving path is 11 basic blocks.
  It ends at 0x401ccc with pc = <BV64 0x0>
  Final stashes: {'errored': 1}   [symbolic]
  angr files it under `errored`, not `unconstrained`: the unfilled
  vtable slot reads as zero, so the branch is to address zero and the
  engine fails on it. Either way the state is gone, and neither is
  reported as a failure by `simgr.run()`.

  The block it dies in:
      0x401ccc  ldr    x1, [x29, #0x18]   <- vtable slot; unfilled, so this read has no answer
      0x401cd0  mov    x0, x1
      0x401cd4  ldr    x1, [x1]   <- vtable slot; unfilled, so this read has no answer
      0x401cd8  adrp   x16, #0x480000
      0x401cdc  add    x16, x16, #0x228
      0x401ce0  ldr    x15, [x16, #0x188]   <- vtable slot; unfilled, so this read has no answer
      0x401ce4  mov    x16, #-0x28
      0x401ce8  movk   x16, #0xffff, lsl #16
      0x401cec  ldr    x16, [x1, x16]   <- vtable slot; unfilled, so this read has no answer
      0x401cf0  blr    x16   <- branch register is whatever that read gave

  This is the shape every loss in this image has: a `callvirt`
  compiled to a load from the receiver's vtable and an indirect
  branch, with no runtime present to have filled the vtable.  [static]

2. IS THE LOSS RECOVERABLE BY CHOOSING A TARGET?
--------------------------------------------------------------------------
  Measured two ways, because the answer depends on how uninitialised
  memory is modelled. Both ways agree.

  angr's default (an unmapped read yields a fresh symbol)
      lost states examined across 6 entry points : 24
        program counter wholly free (pc == 0xdeadbeef satisfiable)  : 23
        program counter fixed or narrowed                        : 1

  this project's model (uninitialised memory reads as zero)
      lost states examined across 6 entry points : 7
        program counter wholly free (pc == 0xdeadbeef satisfiable)  : 0
        program counter fixed or narrowed                        : 7

  Under angr's default the branch register is a fresh symbol nothing
  constrains, so the solver accepts any address at all. Picking one
  invents a path, and the sample may never perform what gets reported
  from it. Under the zero-fill model the register is concretely zero,
  which is no better. Either way the state does not hold the answer.
  [symbolic]

  This is what rejected the first design, which recovered states from
  `unconstrained` by pinning the program counter to plausible in-image
  methods (kept in archive/superseded/tools/managed_explorer.py).

  Which is what the final design rests on: the missing information
  is not in the state, so it has to come from outside -- from the
  original assembly's metadata.

4. WHAT REMAINS UNSUPPORTED, AND WHY
--------------------------------------------------------------------------
  states captured at an unsupported boundary: 7
         7  receiver is null

  These need different repairs. A symbolic receiver comes from an
  earlier unmodelled call, an untyped receiver is an allocator or
  metadata gap, and an unrecognised dispatch shape is a decoding gap.
  Lumped together as 'unconstrained' they look like one problem when
  they are three.  [symbolic]

--------------------------------------------------------------------------
5. WHY RECEIVER-DIRECTED RESOLUTION FIRES AS RARELY AS IT DOES
--------------------------------------------------------------------------
  call sites resolved statically, image-wide : 492
  call sites left to the receiver            : 119
  (declaring type, slot) pairs learned       : 85
  allocation sites carrying a type           : 257

  On the paths measured above the receiver-directed lookup resolved
  nothing. The diagnostics say why: the receivers arriving at
  unresolved sites are objects returned by unmodelled managed calls,
  which carry no type, or values loaded from fields this analysis
  never wrote. Typing an allocation only helps when the object reaches
  the call site through code that actually ran.

  So: a negative result. The mechanism works when it fires, and on
  these two samples it does not fire. The static call-site table is
  what carries the result.  [symbolic]
